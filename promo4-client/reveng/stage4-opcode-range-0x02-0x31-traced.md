# Chasing down the newly-discovered opcode range: `0x02`-`0x05` and `0x16`-`0x31`

Direct follow-up to `stage4-embedded-opcode-table-completed.md`'s closing note, which flagged a whole
additional opcode range below `0x2a` as real, confirmed-to-exist, and completely unexplored. This pass
read every remaining dispatch branch in `ATIR500GLContext::process_command_buffer` across that range in
full, real context - not just categorizing shapes, but reading actual bodies wherever the content
justified it.

## The complete picture, by marker

| Marker(s) | Category | Real behavior |
|---|---|---|
| `0x02`-`0x05` | HyperZ/HiZ block management | Real, non-trivial logic using named HiZ memory-manager functions (`HZMEM_GetBlockOffset`, `HZMEM_GetBlockCount`, `HZMEM_IsPartial`) to compute compressed-Z clear/resolve block ranges. Not traced to full bit-level precision - a deliberate call given the redesign proposal (`stage4-TOP-DOWN-promo4-redesign-proposal.md`) already avoids HyperZ entirely for a minimal draw, so the marginal value of a byte-exact trace here is low relative to the rest of this range. Categorized, not exhaustively decoded. |
| `0x16,0x18,0x19,0x1b,0x1c,0x1e,0x1f,0x21,0x22,0x24,0x25` | Texture unbind (second family) | All branch to the same shared handler (`LAB_0002e820`) already documented for `0x06-0x15` - `uVar38 = uVar38 + 0xea000000 >> 0x16` maps the marker's top byte to a byte offset in the same `this+0x2a4` per-unit slot array. This is the *same* unbind mechanism, just extending the marker range that reaches it - not a new mechanism. |
| `0x17,0x1a,0x1d,0x20,0x23` | **Reserved / dead in this build** | Each has a dedicated `if (uVar38 != 0x1a000000)`-style exclusion from the shared unbind path, implying the dispatch author intended distinct handling - but no corresponding body exists anywhere in the function for an exact match on any of these five values. Falling through the whole if/else chain with no match means these opcodes currently do *nothing* beyond whatever the generic per-record skip does. Real finding: the dispatch structure reserves these five slots (evenly spaced, every 3rd value in a sub-range) for handling this build never implements - most plausibly vestigial from an earlier driver revision, or reserved for a future per-unit variant never finished. |
| `0x26000000` | **GART transfer-buffer bind** | Looks up a texture/transfer-buffer descriptor via the same table used by real texture binds (`this+0x88`), tracks the currently-attached buffer in a distinct per-context field (`this+0x328`, separate from the `0x2a4`/`0x338`/`0x348` texture-unit slots already known), does real refcount increment/decrement bookkeeping, and calls the already-confirmed `map_transfer_to_GART`. A bind operation for a GART-mapped transfer buffer (PBO/DMA-style CPU↔GPU transfer path), architecturally parallel to but distinct from the texture-unit bind family. |
| `0x27000000` | **GART transfer-buffer unbind** | The direct companion to `0x26`: decrements the `this+0x328` slot's refcount, clears it, and falls into the exact same simple marker-erasure tail (`*puVar65 = 0x80000000`, `LAB_0002eae8`) used by the plain texture-unbind family. Confirms `0x26`/`0x27` are a real bind/unbind pair for this transfer-buffer path, mirroring the texture bind/unbind pairs already documented. |
| `0x28000000` | **Single render-target + scissor commit** | Computes a real render-target offset/pitch/tiling value (same formula shape as the already-confirmed `RB3D_COLOROFFSET`/`COLORPITCH` computation) and writes the current `this+0x354`/`this+0x358` scissor-rect fields (the same fields `build_scissor` computes) directly into the command stream, alongside a value at register index `0x50b`. **Note**: `0x50b` (byte address `0x142c`) does *not* correspond to any known R5xx MMIO register in either local register-doc PDF, and this exact index/formula pairing was already seen, unresolved, in `write_kernel_context_buffer_regs`. Seeing it reused consistently here confirms it's a real, driver-internal *software* bookkeeping field embedded in the command stream for cross-referencing between opcodes - not a raw hardware register at all. This is a useful methodological clarification: **not every `(index, value)` pair in this convention targets real MMIO** - some are private software protocol fields the kernel-side code reads back out of its own generated stream. |
| `0x29000000` | **Vertex-format configuration + full pipeline commit** | A real switch statement mapping small enum values (`0,1,2,3,7,8,0x10,0x11`) to internal semantic-slot codes (consistent with `GL_COLOR_ATTACHMENT`/depth/stencil-style binding-point enums, matching the same table shape already seen in `0x2a`'s attachment-enum lookup). Tracks a count in `this+0x3a8`. **Directly calls `build_scissor(this)` and `write_kernel_context_buffer_regs(this, puVar65, 0, puVar65[6], puVar65[7])`** - the exact same register-serializer function already fully decoded (`stage4-write-kernel-context-buffer-regs-fully-decoded.md`) as the handler behind opcode `0x41`. This is a genuinely valuable cross-reference: `write_kernel_context_buffer_regs` is now confirmed to be a *shared*, reusable "commit full render/framebuffer state" primitive invoked from at least two independent opcodes (`0x29` and `0x41`), not something specific to render-target binding alone - plausibly `0x29` is emitted once per draw call to finalize vertex format together with the rest of pipeline state. |
| `0x2a000000` | Render-target-pair + scissor | Already documented in `stage4-embedded-opcode-table-completed.md`. |
| `0x2b000000` | **Explicit client-triggered flush** | If a pending count (`local_384`) is non-zero, directly calls `ATIRadeonX1000::submit_buffer` (the same real submission path used elsewhere), advances local bookkeeping, then self-erases (`*puVar65 = 0x80000000`). Unlike the "flush if buffer nearly full" pattern seen throughout the rest of this driver (an automatic, capacity-driven flush), this is a *named, client-emitted* marker - real evidence the client-side API can request an explicit flush point mid-stream (a GL-`glFlush`-equivalent primitive expressed in this marker language), independent of buffer capacity. |
| `0x2c000000` | **Mip/slice-aware scissor intersection** | Computes a render-target offset/pitch value for a specific mip level (indexing consecutive mip offsets via `iVar33`/`iVar33+1`, the same subtraction-of-adjacent-mip-offsets pattern used for pitch derivation elsewhere), then intersects the resulting rectangle against the *current* `this+0x354`/`this+0x358` scissor fields via real min/max clamps, writing the intersection back. Complements `0x28`/`0x2a` (which *set* the scissor): this opcode *narrows* an existing computed rect to whatever scissor is already active - real support for rendering into a specific mip/slice of a surface without exceeding the active clip region. |
| `0x2f000000` | **HyperZ configuration commit** | Directly calls the already-known `compute_sc_hyperz_en` and `compute_zb_bw_cntl` (the exact two functions `stage4-render-target-and-full-draw-reference.md` decoded as this driver's real HyperZ enable/bandwidth-control decision logic), patches their results into the embedded slots, then makes a vtable call (`(**(code**)(*(int*)this+0x5a4))(this)`). This is the real, confirmed client-emitted trigger for HyperZ setup - directly confirming the corollary already inferred: if a client never emits `0x2f`, HyperZ configuration never happens beyond whatever default (off) state the hardware/driver starts in. Strengthens the redesign proposal's basis for skipping HyperZ by simply never emitting this opcode. |
| `0x30000000` | **FSAA resolve-buffer setup** | A switch statement mapping small format-ish values to internal codes, then calls the real, named `ATIR500Surface::resolve_fsaa_buffer` with the mapped code plus several embedded parameters, and patches a completion header (`0xc0001000`-style Type-3 NOP) after the call if room remains. A real trigger for resolving a multisampled (FSAA) render target down to a plain surface. |
| `0x31000000` | **Full state-restore blit, FSAA-resolve variant** | The richest single find in this range. Builds a complete `r500_3d_blit_state_packet` using **`FUN_000314c4(puVar65, &_g_r500_3d_blit_state_packet, 0x2f4)`** - the exact same 0x2f4-byte global template already fully mapped register-by-register in `stage4-complete-register-tracking-state-map.md` as the one used by `restore_state_destroyed_by_pageoff`. It computes real per-mip render-target offset/pitch/tiling values for *two* surfaces at once (a main buffer `pAVar77` and a second, resolve-target buffer `pAVar72` - consistent with this opcode being FSAA-adjacent, sitting right next to `0x2c`/`0x30`), then builds a complete textured full-quad draw: real floating-point NDC/viewport coordinate math (tile-aligned to the R5xx's 0x200/0x40 macro-tile granularity), a `0x31080`-header draw-immediate packet, `US_ALU`-area shader-instruction headers (`0xc0033500`/`0x10031`, in the same register-index family as the already-confirmed `US_ALU_RGBA_INST_VAL`/`GA_US_VECTOR_INDEX` shader-load registers), and texture coordinates for the resolve source. **This is a complete, real, second confirmed example of "blit via a textured full-screen quad plus a shader pass"** - the same technique `_radeon3DCopySetup`/`_radeon3DFillSetup` already proved works on real hardware (`stage4-radeon3DCopySetup-complete-draw-reference.md`), now seen a second time, independently, inside the kext itself, applied to FSAA resolve specifically. |

## Real, previously-unstated pattern this range confirms

`write_kernel_context_buffer_regs` and `_g_r500_3d_blit_state_packet` (the two central "write the whole
pipeline state out" mechanisms this project has fully decoded) are not single-purpose functions tied to
one opcode each - they are **shared primitives invoked from multiple, functionally distinct opcodes**
(`0x29` and `0x41` call the former; `0x31` and `restore_state_destroyed_by_pageoff` use the latter
template). Any from-scratch client implementation that wants to replicate "commit full render state"
now has *two* independently-confirmed, real call sites to cross-check register content against, not one.

A second real pattern: **not every value the client embeds in this marker language is a raw hardware
register.** `0x28`'s `0x50b`/`0x142c` index, seen consistently across two independent opcodes now, is a
private software bookkeeping field the driver's own generated stream carries and later reads back - a
genuine distinction future tracing work in this project should keep in mind before assuming every
`(index, value)` pair maps to real MMIO.

## Honest limits

- `0x02`-`0x05`'s HyperZ/HiZ logic is categorized, not traced to bit-level precision - a deliberate
  scoping choice given its low relevance to a HyperZ-avoiding minimal draw, not a static-analysis
  ceiling.
- `0x17`, `0x1a`, `0x1d`, `0x20`, `0x23` are confirmed dead/no-op in *this specific kext build* by
  exhaustive dispatch-chain reading, not by any external documentation - there is no way to rule out
  they were live in some other driver revision.
- `0x2c`, `0x2f`, `0x30`, `0x31` are read and understood at a real, meaningful level of detail but were
  not re-verified against register documentation the way the capstone map's entries were - their
  register-index values are cited from the already-confirmed capstone map and shader-constant findings,
  not independently re-derived from the PDF text here.
- Nothing in this document was tested on hardware. Every finding is static analysis only, per the
  standing constraint for this session (no G5 access). No hardware test is proposed for this range
  specifically - everything here is either explicitly redundant with mechanisms the existing redesign
  proposal already plans to test (the shared register-commit primitives, the textured-quad blit
  technique) or explicitly out of scope for that proposal (HyperZ, FSAA resolve, transfer buffers).
- The full `0x02`-`0x46` opcode range this project has now encountered is believed complete - no further
  dispatch-chain edges pointing to unread territory were found while reading this range end to end.
